# ConcordRTS：用 C++20 重写红警 2 的引擎

> 值得记录的不是"又一个开源红警"，而是它把"这次验证不能证明什么"写成了每条更新的固定句式。

- 状态：草稿
- 最近核验：2026-10-30（阅读 README 全文、目录结构、提交记录与 GitHub API 元数据，未编译、未运行）
- 适用范围：Windows（日常构建为 clang-cl + Ninja，保留 MSVC 参考入口）；面向 RA2/YR 的规则、地图与资源格式

## 核心结论

一个用 **C++20 从零重写**的 RTS 引擎，目标是兼容《命令与征服：红色警戒 2》与《尤里的复仇》的**规则、地图和资源格式**。仓库只公开作者自编的引擎源码、构建工具、测试代码与示例，**不含原版游戏程序与官方素材**——运行所需的游戏数据由使用者自己准备。

功能面铺得很开：遭遇战、AI、战役、局域网与互联网联机、观战、存档与联机恢复，另有规则分析、地图解析、资源读取与导出工具。

**渲染路线是它最有意思的取舍**：主战局**默认用软件绘制（GDI）**，可选 D3D11 完整帧呈现、可选地图 GPU 绘制（地形、材质、阴影、光照、迷雾、VXL）；而**资源解码、几何、地形查询、视野与模拟始终由 CPU 原实现负责**。作者反复强调硬件与 WARP 分开选择、`auto` 当前仍选软件、**GPU 只承接绘制而不接管权威状态**。

README 里最突出的特征是**结论边界写得极严**：几乎每条更新的结尾都在声明"这些结果覆盖哪些场景、不能推出什么"。例如"当前测量未证明整体加速"、"本机验收脚本与采样数据不随源码发布"、"局部并行验证不代表整个模拟已经并行化"。**这一节本身就可以当作技术写作范本。**

## 关键技术点

**双窗口与多呈现后端**

- 遭遇战菜单可选择 **Win32 或可选的 SDL3 软件窗口**，确认后进入 Win32 战局；
- 主战局默认**软件绘制 + GDI 呈现**，可显式选择 **D3D11 完整帧呈现**（地图、界面、FPS、软件鼠标仍由 CPU 组成后上传），也支持地图 GPU 绘制路径；
- 资源预算与设备恢复做了完整处理：资源复用、缩放与换代先等上一帧完成（等待有时限），设备失效时保留同帧软件回退，并在可见窗口中按冷却与次数上限尝试重建。

**确定性优先的并行化**

- 地图屏幕块命令索引准备可走有界任务执行器：`--frame-workers 0|1|2|4`，**默认 0 保留原参考算法**；
- 寻路初始目标候选有 `reference / shadow / parallel` 三档（`CONCORD_PATH_CANDIDATE_MODE`），**`shadow` 只对照、仍返回原同步结果**——这种"先影子运行再切正"的推进方式很值得学；
- 每帧最多四个任务，各自持有输入/输出/工作区，按屏幕块与原命令序号稳定合并，**过期结果只影响显示，不进入业务或音频事件队列**。

**结构防回退工具**

[structure-baseline.json](https://github.com/AdrianLuo-X/ConcordRTS/blob/main/tools/structure/structure-baseline.json) 里保留着 **4,696 条逐项审核过的精确例外**，检查模块依赖、平台类型、源码归属、测试注册与编译参数。新增违规、出现次数增加、或"例外已消失但尚未收紧"都会让检查失败，**工具不会自动扩大豁免范围**——这是少见地把"技术债不能悄悄变多"写成自动检查的做法。

**测试与验收（作者自述）**

以 2026-10-29 那次记录为例：1,438 项纯模块检查、1,287 项原生检查、27 项相关 CTest、66 个结构夹具检查。**但作者同时声明"不表示全部注册测试或所有设备环境均已通过"**，并列出了已知仍失败的项目：月球剧场深度、部分交互与几何绘制、Yuri 采矿收入、完整 AI 经济、部分编队紧凑度、矿石动画。

## 使用前需要注意

- **必须自备原版游戏数据**：仓库不含游戏 EXE/DLL、图像、模型、调色板、音频、视频、字体、官方地图、完整原版规则文件，也不含从 MIX 提取的内容。README 说"运行所需的游戏数据由使用者自行准备"，**没有给出体积或清单**，建议在动手前先确认自己手上的安装包能否满足其资源搜索路径（`RedAlert2/`、`local_data/` 等）。
- **提交历史不反映真实开发过程（重要）**：README 的"上传 GitHub"一节明确说明工作流——**从私人开发工程复制源码到独立仓库再推送，且不要带走原工程的 `.git`**；实际提交记录也确实如此：21 次提交，信息多为"GPU 实际绘制第一个完整 UI/精灵场景"、"每完成一部分地图 GPU 绘制，就保存一次"这类**里程碑式批量快照**。因此**不能把提交时间线当作代码审计时序**，也看不到细粒度的修改理由。这与 [ra2](ra2-浏览器运行红色警戒2.md) 的"开源快照"模式是同类现象。
- **兼容性是渐进目标，不是承诺**：作者明说"不保证原版所有细节、全部战役或任意第三方 MOD 均已完整兼容"，且上面的已知失败项都有记录。**把它当"可研究、可贡献的引擎工程"而不是"能替代原版的成品"**。
- **构建与验证有前置条件**：需要 Windows Clang 工具链与本地素材；部分测试需要**真实图形环境与交互桌面**（D3D11 与菜单光栅合同会实际创建窗口、分别检查硬件与 WARP），**无素材环境下的编译成功不代表功能通过**。
- **性能结论要按原话读**：作者反复说明"所选阶段计时不构成全游戏加速结论"，设备探针、CPU 提交间隔、实际显示帧率是三个不同指标，**当前工具并没有测量游戏 GPU 帧时间或屏幕输出帧率**。
- **GPL-3.0-only 的传染性**：作者自编部分采用**仅第 3 版**的 GPL。若你打算把它的代码并入其它项目，需遵守 GPLv3；同时**该许可不包含原版 RA2/YR 的程序、素材或商标授权**，商标与素材权利仍归各自权利人。
- **我只读了 README、目录结构与提交记录，没有编译、没有运行**：功能完成度、构建可复现性、性能说法均未独立验证。

## 什么时候会再看

- 想研究**"如何把 GDI 软件渲染的旧引擎逐步接入 D3D11 而不改变权威状态"**时：软件回退、资源代际、设备恢复、同帧回退这一整套处理都有源码。
- 想参考**"并行化如何做到可回退、可对照"**时：`reference / shadow / parallel` 三档模式与"过期结果只影响显示"的边界非常具体。
- 想参考**"已知问题与验证边界怎么写"**时：更新记录里"测量不能推出什么"的句式，可直接搬到自己的项目里。
- 想参考**"结构防回退基线"**时：4,696 条审核过的精确例外 + 不允许自动扩豁免，是把架构约束落成 CI 门禁的实例。
- 需要**解析 RA2/YR 的地图、规则、SHP/TMP/VXL/PAL 资源格式**时：`src/assets/` 与 `src/data/rules/` 是少见的完整开源实现。
