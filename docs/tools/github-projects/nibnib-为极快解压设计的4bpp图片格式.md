# nibnib：为"极快解压"设计的 4bpp 图片格式

> 一个把**解压速度**当唯一目标的图片格式：解码一次吃一个字节、吐两个像素，目标是在 RP2350 这类单片机上做到约 6 周期/像素。它和 [squoosh](squoosh-浏览器内的图片压缩工具.md) 正好是两个极端——那边求压缩率，这边求解压速度，编码慢几个数量级也认。

- 状态：草稿
- 最近核验：2026-11-03（阅读 README 全文、仓库结构、双许可文件与 GitHub API 元数据；**未编译、未用该格式编解码任何图片**）
- 适用范围：嵌入式显示（低端 MCU 上的 DVI/帧缓冲输出）方向的格式设计参考；**不是**日常图片压缩工具

## 核心结论

1. **它是"解码优先"的格式**：整个格式由解码过程定义，解码简单且确定，所有复杂度都推给编码器。作者明说**编码比解码慢好几个数量级**，并且**当前编码器并不自适应输入图像**——调色板是固定的"小 delta 立方 + 随机高斯值"，这被列为最大的改进空间。
2. **4bpp 的来历是"一次两个像素"**：解码以像素对为单位，把上一个像素**复制成双份**，再从输入读一个字节查调色板，得到一个 32 位增量加回去，就同时产出两个 RGB565 像素。所以每字节出两像素 = 4bpp，省掉的是"每个像素都要一个索引"的开销。
3. **调色板存的是"增量"而不是绝对色**，这是它质量能超过普通调色板图的关键，作者说这是"soft region"（柔和区域）改善的主因；纯随机调色板会产生明显伪影，必须有小 delta 立方兜底。
4. **项目极新且极简**：2026-10-30 创建，我核验时才 4 天；仓库只有 `Cargo.toml`（353 字节）、`src/`、`images/` 与两个许可文件，**无 Release、无 Tag、无 topics**。作者在 README 里明确写了"这个格式不打算用于归档"。

## 它是怎么工作的

**解码（确定性、极简）**：把上一个解码出的像素复制成双份，从输入流读一个字节并在调色板中取值，把这个 32 位值加到"双份的上一个像素"上，就得到两个 16bpp（RGB565）像素，低 16 位是左像素。README 给出的内层循环（略作改编）：

```rust
    // first two pixels copied from src[0..4], initializing pix
    for x in 1..(width / 2) {
        let inp = src[x + 3];
        pix = ((pix >> 16) * 0x10001).wrapping_add(pal[inp as usize]);
        out[x * 2] = pix & 0xffff;
        out[x * 2 + 1] = pix >> 16;
    }
```

`0x10001` 就是"把低 16 位复制成两份"的乘法技巧——一行里同时体现了像素复制与增量相加。

**编码（搜索式、很慢）**：两个搜索维度是**调色板选择**与**码字选择**。当前实现里概念上就是"试遍 256 个调色板项、取误差最小的那个"，再用 **Floyd-Steinberg 误差扩散**把误差按权重分摊给后续像素。与常见的误差扩散不同，它是**一次为两个像素同时选一个调色板项**，并且给"两像素之和"更高的权重——理由是模型假设人眼对**低空间频率更敏感**。

代价写在明面上：伪影会**拖在锐利边缘的右后方**，这是贪心搜索的后果。作者也把解法写清楚了（改成从右往左、甚至逐行蛇形交替，但解码仍是左到右，因为加法在实践中可逆）。

**文件格式**（极简，无元数据）：

```text
2 字节宽 + 2 字节高
256 × 32bit 调色板项
逐行：每行先 2 个像素（RGB565），随后 ((width - 2) / 2) 个字节，每字节索引调色板
行跨距向上取整到 4 字节的倍数
```

README 明确说**没有其他元数据、不用于归档**，更可能的用法是与解码器紧密集成（例如直接把解码器烧进 MCU）。仓库里的解码器是 Rust 实现，**RP2350 上的实时解码实现放在另一个仓库 [vic-2350](https://github.com/raphlinus/vic-2350)**。

## 使用前需要注意

- **未编译、未编解码任何图片**：我不清楚它在真实图片上的体积/画质表现，也没有验证 README 里那些对比图的实际效果。
- **它是"格式与算法"，不是"即用工具"**：仓库很小、没有 Release 与 Tag，也没有命令行工具或 Cargo 包发布信息（本次未核验 crates.io 是否已发布）。想用基本等于读源码自己接。
- **编码器当前是"原始版本"**：调色板固定、非自适应，作者自己列了三类改进方向（调色板优化、更深的误差最小化搜索、编码提速），并注明这些改进**都能在现有解码器不变的前提下完成**——这恰好说明"解码定死、编码随便换"是它的核心约束。
- **不适合通用场景**：4bpp 调色板 + RGB565、无元数据、边缘伪影向右拖尾。**要压照片还是用 [squoosh](squoosh-浏览器内的图片压缩工具.md) 那类工具**。
- **项目太新，别急着下结论**：4 天、2 个开放 Issue、0 关注者。它现在更像一份"公开的实验记录"，作者在 README 里的写法（把取舍、失败模式和改进方向都摊开）本身就值得当参考。
