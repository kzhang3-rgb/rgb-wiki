# nv-uefi-unlocker：在驱动加载前解锁 NVIDIA 显卡的算力钳制

> 记录这个工具改的是哪一层、为什么要从 U 盘启动，以及"不刷 VBIOS、断电复原"这套设计挡不住哪些风险。未下载发布包、未制作启动盘、未在机器上运行。

- 状态：草稿
- 最近核验：2026-11-03（阅读仓库 README、致谢清单与 GitHub API 元数据；未下载发布包、未写盘、未在任何显卡上运行）
- 适用范围：GTX 16（作者称理论兼容）/ RTX 20 / RTX 30 / RTX 40；目标机需 UEFI 启动，并关闭 Secure Boot 或自签 EFI 并信任；**不支持** Pascal 及更早、GA100、RTX 50

## 核心结论

这是一个**在 NVIDIA 驱动加载之前**运行的 EFI 程序：从 U 盘启动，把出厂被钳制在"半速"的张量计算路径解锁，随后自动链回本机原本的系统，无需刷写 VBIOS，**断电后恢复原状**。

它改的不是超频参数，而是**显卡固件/寄存器层面的算力策略**，所以不做持久化落盘——代价是**每次冷启动都要重放一遍**。

值得记的不只是功能：仓库的致谢清单列出了完整的上游谱系（Zagitta 的 `gpu-unlock` 是事务链移植母本、`gpu-unlock-ada` 是四写链源头等），并声明"事务代码是上游 GPL-2.0 实现的行为级移植，须先通过行为级模拟器全绿、再经实机读回验证才进入发布"。**这种把来源、验证链路和失败恢复都摊开写的做法，比同类硬件工具透明得多**，也是我把它收进笔记的主要原因。

## 它解决什么问题

作者的主张是：RTX 20–40 世代的部分张量计算路径在出货时被钳制在半速。逐精度口径（作者自述，我未验证）：

| 精度档 | 出货钳制 | 作者给出的理论上限 |
| --- | --- | --- |
| FP16 / BF16 / TF32（FP32 累加张量路径） | 半速出货 | 2× |
| FP8（E4M3/E5M2，SM89+） | 半速出货 | 2× |
| FP16（FP16acc）/ INT8 / INT16 / INT32 / FP32 / FP64 | 无（出厂全速） | 1× |

作者实测口径为：FP16/BF16/TF32 最高约 **2.6×**、FP8 最高约 **1.9×**、图像/视频生成 **+14–75%**、DirectML 推理算子最高 **+94%**、LLM 推理 prefill 最高 **+19%**（decode +5%）。同时明说**实际倍数受功耗墙、显存带宽与逐 die 分箱制约，典型 1.5–2×**，LLM 数据来自双卡 MoE 实测而非微基准外推；CMP 矿卡是例外（被除以 32，上限反而 32×）。**以上全部是作者口径，逐卡数据在 `docs/compatibility.md`，我没有验证。**

## 怎么用（README 三步）

1. **取工具并查前置**：从 Releases 下载解压；准备一个 FAT32 U 盘并**先备份其中文件**；目标机 UEFI 启动、关闭 Secure Boot（或自签信任）。Turing 卡需先在目标 Windows 的管理员 PowerShell 跑一次 `.\enable-turing-unlock.ps1` 再重启。
2. **在目标机做启动盘**：直接运行 `make-usbroot.ps1`（或 `bash make-usbroot.sh`），脚本按本机显卡代际只生成对应固件，产出在本地 `usbroot/`；把**内容**复制到 U 盘根目录（不要拷成 `U:\usbroot\`）。
3. **启动并验证**：从一次性启动菜单选 U 盘，版本屏按空格/回车执行，日志写在 U 盘根目录 `loader.log`；Windows 下用发布包的 `ssdiag-x86_64-windows.exe` 查状态并对比解锁前后性能。

README 还为"让 Agent 代做"提供了 `AGENTS.deploy.md`——可以直接把一段提示词交给 AI 助手按步骤执行。仓库另说明构建路径（`rustup target add x86_64-unknown-uefi` + `cargo build --release` + `cargo efi-tx`）。

## 使用前需要注意

- **它要求关闭 Secure Boot**：这是最实质的代价。无论是临时关还是自签 EFI，都削弱了这台机器原有的启动链完整性保护；用完是否记得恢复，取决于你自己。
- **失败不是零成本**：README 写明"遇到 STOP、异常或黑屏卡死，**同会话不要重试**；完全断电后拔 U 盘，走原系统引导"，再按恢复说明排查。作者称"从 U 盘一闪回到启动菜单"时**没有任何写入**（多因缺 `EFI/BOOT/BOOTX64.EFI` 或 Secure Boot 还开着）——这是它相对安全的论据，但**"断电复原"指的是不持久化改动，不等于所有异常场景都无副作用**。
- **每次冷启动都要重放**：它不是一次性设置，属于"每次开机前过一道"的流程。Linux 用户还需注意 RTD3，否则进系统后可能掉电丢失解锁状态。
- **属于固件/寄存器层面的非官方操作**：可能触碰保修、平台条款或地区法规，README 未就此类问题表态。**本笔记只作信息记录，不代表建议，也不对合规性作判断。**
- **性能数字与兼容性均未由我验证**：上表与百分比都来自作者自述与仓库内矩阵；部分型号作者标注"有已知问题"。
- 与 [nvoc](https://github.com/Skyworks-Neo/nvoc) 叠加使用会突破原厂功耗与温度包络，README 自己提示需自行确认散热与供电余量。
- **相关工程写法值得单独看**：README 收录了三个"闭环案例"（魔改 VBIOS 的 P8 锁误判、CSM 交棒定律、雷电解锁的 staging 低位化），每个都附完整日志与证据链，其中 P8 锁一例记录了**四层误导被逐层剥开**的过程。这类"把诊断过程当产物写出来"的仓库不多见。
